**总建议：值得做，但先别写代码。**

2. 验证通过后，把定位从「全链路研究服务」改为**「先分诊、再深挖、可验证的个人决策助手」**：默认只做 1–3 分钟的速判，值得的才进入完整链路。
3. 技术上用托管 Agent 平台 2–3 周跑通 MVP，精力集中在真实性判断层，这是整个项目唯一真正的护城河。

> **v2 更新**：你确认了首要目的是**省事**。据此，推荐方案从「托管 Agent 平台 + 自写工具」进一步简化为**路线 0**：直接在本仓库里用 Claude Code 的 Skills、子 Agent、云端会话和定时任务来搭，开发量从 2–3 周降到 1–2 天，几乎零维护。今天就能用 `prompts/build-prompt.md` 里的「立即可用版」提示词开始。详见第 9 节。

### 1.2 你没明说、但我推断你需要的东西

1. **过滤炒作**：「网上看到的有趣项目」里有大量营销、刷星、PPT 产品、夸大宣传。你真正想知道的往往是「**这东西是真的吗？值得我花时间吗？**」。所以你把「真实性判断」单列为一环，我认为这是整个想法里最有价值的直觉。

4. **可追溯**：报告里的每个关键结论，你都应该能点开看到原始出处。

## 2. 想法延伸：从「研究流水线」到「面向决策、可验证的研究助手」

### 2.1 六个关键重构

**重构 0：先分诊，再研究（最重要）**

网上看到的「有趣项目」，绝大多数只值得花 2 分钟，不值得花 45 分钟和 7 美元。把每个输入都跑完整的六段链路，会产出大量你根本读不完的报告。所以系统的默认动作不应该是「研究」，而应该是「分诊」：

| 档位 | 耗时 | 估算成本 | 产出 | 何时触发 |
|---|---|---|---|---|
| **速判（默认）** | 1–3 分钟 | 不到 0.5 美元 | 5 行：它是什么 / 真实性初判 / 和你有没有关系 / 建议（忽略·收藏·深挖）/ 理由 | 所有输入 |
| **标准** | 15–30 分钟 | 4–12 美元 | 完整的六段报告 | 速判结论为「深挖」，或你点名要 |
| **深度** | 30–90 分钟 | 15–30 美元 | 再加沙箱复现、横向对比 | 要投入真实资源（时间、钱、职业选择）的决定 |

速判本身就是一次「真实性 + 相关性」的过滤。它会是这个系统每天用得最多的功能，也最能直接解决「信息太多、判断太少」的问题。

**重构 1：线性流水线 → 研究循环**

真实的研究不是一条直线。分析到一半常会发现「这个数据缺了」「两个来源说法矛盾」，这时要**回到检索**。建议把链路设计成一个有状态的图（graph）：每个阶段都可以向主控 Agent 报告「缺口」，主控在预算内决定是否回去补检索。

```text
你的原设计：  搜索 → 背景 → 事务研究 → 具体分析 → 真实性 → 交付

建议设计：    意图澄清 → 规划 → ┌→ 检索 → 阅读/抽取 → 分析 ┐ → 终审核查 → 交付
                                  └──── 发现缺口/矛盾时回到检索 ┘
                                       （每份报告设预算和轮次上限）
```

**重构 2：真实性判断从「末端一环」变成「贯穿全链路的一层」**

只在末尾核查，前面吸收的错误信息早已影响了分析框架。建议分三道关：

| 关口 | 时机 | 做什么 |
|---|---|---|
| 第一道：**来源分级** | 检索入库时 | 给每个来源打可信度等级（一手/权威/二手/社交），标出利益相关方（项目方自己的宣传 ≠ 独立评测） |
| 第二道：**主张核验** | 写作之前 | 把分析中的每条关键事实拆成「原子主张」，逐条找证据，判定为已证实、部分证实、证据不足或与证据矛盾 |
| 第三道：**红队审查** | 交付之前 | 由一个独立的「挑刺 Agent」站在反方立场审稿，专找过度推断、引用错配、遗漏的反面证据 |

**重构 3：区分两种「真实性」**

| 类型 | 问题 | 例子 |
|---|---|---|
| **信息真实性** | 这句话是真的吗？ | 「该模型在 X 基准上超过 GPT」，原文是这么说的吗？是独立复现的吗？ |
| **项目真实性** | 这个项目本身靠谱吗？ | GitHub 一周 1 万星是自然增长还是刷的？Demo 能跑吗？团队是真实存在的吗？ |

第二类是大多数通用研究工具**不做**的，恰好是你的差异化机会（详见 3.3 节）。

**重构 4：重新界定中间三段的边界**

你的「背景调研 / 事务研究 / 具体事务分析」三段边界有些模糊，实现时容易重复劳动。建议这样定义：

| 阶段 | 回答的问题 | 典型产出 |
|---|---|---|
| **背景调研** | 它是什么？谁做的？从哪来？周围有什么？ | 一句话定义、团队/作者、时间线、融资/资助、竞品与前作 |
| **事务研究** | 它是怎么运作的？ | 技术原理/架构、商业模式、数据与指标、关键依赖 |
| **具体事务分析** | 这对**我**意味着什么？ | 优劣势、风险、机会、和你目标的匹配度、情景推演、**下一步行动建议** |

最后一段必须带上**你的个人上下文**（你的目标、技能、资源、时间），否则只是一份通用报告，和 ChatGPT 的深度研究差别不大。

**重构 5：入口先识别意图**

同一个项目，「我想学它」「我想用它」「我想做个竞品」「我想投它/加入它」，研究重点完全不同。建议在入口加一个**意图识别 + 最多 3 个澄清问题**的环节。你不想回答时就套用默认画像，产出一份结构化的「研究任务书」（Research Brief），作为后续所有 Agent 的共同依据。

### 2.2 延伸能力清单（按优先级）

| 能力 | 解决什么问题 | 优先级 |
|---|---|---|
| **速判分诊**（忽略 / 收藏 / 深挖） | 大部分输入不值得深度研究；防止把信息囤积自动化 | P0 |
| **意图识别与研究任务书** | 研究目标不清，报告失焦 | P0 |
| **双模式**：项目尽调模式 / 方向扫描模式 | 两类输入需要完全不同的研究流程 | P0 |
| **证据仓库**（网页快照 + 抓取时间 + 内容哈希） | 网页会改、会删，报告结论需要可追溯 | P0 |
| **主张账本**（Claim Ledger）：报告由账本生成，不靠自由发挥 | 从结构上抑制大模型编造与引用错配 | P0 |
| **分层输出**：3 行结论 → 决策卡片 → 正文 → 证据附录 | 不同场景需要不同的阅读深度 | P0 |
| **项目真实性体检**（GitHub/论文/公司/社交帖子） | 过滤刷星、PPT 项目、夸大宣传 | P1 |
| **沙箱复现**：在隔离容器里克隆仓库、跑 Demo、记录结果 | 「能不能跑」是最硬的真实性证据 | P1 |
| **中英双语检索**，中文结论引用英文一手来源（反之亦然） | 很多中文二手信息是英文原文的转述甚至误读 | P1 |
| **个人知识库**：历史报告入库，新研究自动关联旧研究 | 避免重复研究，形成知识复利 | P1 |
| **关注列表（Watchlist）**：定期复查已研究项目，只推送变化 | 项目是动态的，一次性报告会过期 | P2 |
| **多项目横向对比模式** | 「这 3 个同类项目选哪个」是高频需求 | P2 |
| **低摩擦入口**：浏览器插件、手机分享、Telegram/飞书机器人、邮件转发 | 你的输入来自「网上看到」，入口越顺手，用得越多 | P2 |
| **人工检查点**：研究计划确认、终稿确认（可关闭） | 高价值研究里，你的 1 分钟纠偏胜过 Agent 半小时 | P2 |

## 3. 推荐架构（基于 2026 年 11 月的技术栈）

### 3.1 总体架构

```text
【入口层】
  浏览器插件 / 手机分享 / Telegram·飞书机器人 / CLI / 邮件转发
  （输入可以是一个链接、一段文字，或几个研究方向）
        │
        ▼
【0 意图识别与分诊】  识别输入类型与研究目的，先做 1–3 分钟速判
        │             速判结论：忽略 / 收藏 / 深挖（只有「深挖」才继续往下走）
        │             深挖时必要的话问你 1–3 个问题，产出研究任务书（Research Brief，JSON）
        ▼
【主控 Agent（Lead）】  拆子问题、分配子 Agent、管预算、判断是否回到检索
        │
        ├──► 【1 检索 Agent 群】  中英多引擎并行检索、去重、来源分级 ──► 证据仓库
        │                                                    （快照 + 时间戳 + 哈希）
        ├──► 【2 背景调研 Agent】  团队、时间线、竞品、前作
        │
        ├──► 【3 事务研究 Agent】  原理、架构、商业模式；可在沙箱里跑代码复现
        │
        ▼
【4 具体事务分析】  结合你的个人画像：优劣、风险、机会、行动建议
        │
        ▼
【5 真实性判断】  主张账本 → 逐条核验 → 项目真实性体检 → 红队审查
        │         有缺口或矛盾时回到第 1 步（受预算与轮次上限约束）
        ▼
【6 交付引擎】  先生成 Markdown（唯一源文件）
        │       报告里有图片 → 同时导出 Word（.docx）
        ▼
【沉淀层】  个人知识库（历史报告、实体、关系）＋ 关注列表（定期追踪变化）
```

### 3.2 各阶段设计

| 阶段 | 目标 | 执行者（建议模型） | 主要工具 | 产出物 |
|---|---|---|---|---|
| 0 意图识别与分诊 | 先速判值不值得研究；再明确研究什么、为什么研究、研究到多深 | 主控（Claude Opus 5.5，低 effort） | 你的个人画像、知识库检索（看是否研究过） | 研究任务书 |
| 主控规划 | 拆 3–6 个子问题，分派任务，控预算 | 主控（Claude Opus 5.5，高 effort） | 子 Agent 调度、任务预算 | 研究计划 |
| 1 检索 | 找全、找准、找一手来源 | 检索子 Agent（Claude Sonnet 5.5） | 英文搜索 API、中文搜索 API、学术检索、GitHub API、网页抓取 | 证据仓库条目 |
| 2 背景调研 | 建立全景认知 | 子 Agent（Claude Sonnet 5.5） | 同上，外加公司/融资数据源 | 背景章节草稿 + 主张 |
| 3 事务研究 | 讲清机制 | 子 Agent（Claude Sonnet 5.5，复杂技术题用 Opus） | 代码沙箱、论文阅读、仓库代码阅读 | 机制章节草稿 + 主张 + 复现记录 |
| 4 具体事务分析 | 给出「对你意味着什么」 | 主控（Claude Opus 5.5，高 effort） | 个人画像、代码执行（做定量计算） | 分析章节 + 行动建议 |
| 5 真实性判断 | 核验每条关键主张、体检项目真伪 | 核验 Agent（批量初筛 Claude Haiku 5.5，疑难项升级到 Sonnet）+ 红队 Agent（Opus） | 网页抓取 + 原文比对、GitHub 统计、沙箱复现 | 主张账本（含判定与置信度）、红队意见 |
| 6 交付 | 生成可读、可追溯的报告 | 主控 + 渲染脚本 | Markdown 模板、pandoc / python-docx、matplotlib / Mermaid 渲染 | `.md`（以及有图时的 `.docx`） |

> **模型分层的逻辑**：判断和写作交给最强的模型，大量的阅读和抽取交给便宜的模型。成本主要花在「读网页」上，不在「写报告」上（见 4.3 节）。

### 3.3 真实性判断层（护城河，重点设计）

#### 3.3.1 来源分级标准

| 等级 | 类型 | 例子 | 默认可信度 |
|---|---|---|---|
| T1 一手 | 原始出处 | 官方文档、代码仓库、论文原文、监管文件、财报、官方公告 | 高（但要注意利益相关） |
| T2 权威二手 | 有编辑把关的独立方 | 主流媒体、同行评审综述、知名独立评测机构 | 中高 |
| T3 一般二手 | 无严格把关 | 个人博客、聚合站、SEO 内容站、厂商撰写的「对比文章」 | 中低 |
| T4 社交 | 用户生成内容 | 推文、小红书、知乎回答、Reddit、公众号转载 | 低（只作线索，不作证据） |

> 实例：我这次为写本报告做的检索里，搜索 API 的价格对比大多出自其中一家厂商（Parallel）的博客。这就是典型的「T3 + 利益相关方」，所以我在报告里都标了「厂商口径」。你的系统应该**自动**做这种标注。

#### 3.3.2 主张核验流程

```text
草稿 ──► 拆成原子主张（只保留可核验的事实性陈述）
     ──► 每条主张：检索证据 → 抓取原文 → 逐字比对引用片段 → 判定
     ──► 判定结果写入主张账本，报告正文只能引用账本里的条目
```

判定标签建议统一为：

| 标签 | 含义 |
|---|---|
| **已证实** | 至少 2 个相互独立的来源支持，其中至少 1 个为 T1/T2 |
| **部分证实** | 有支持证据，但只有单一来源，或数字/细节不完全吻合 |
| **证据不足** | 找不到可靠证据，既不能证实也不能证伪 |
| **存疑** | 只有利益相关方自己的说法（如项目方自己宣传的基准分数） |
| **与证据矛盾** | 可靠证据与该主张相反 |

**为什么要逐字比对**：2026 年的研究（CiteAudit、CiteCheck）表明，大模型在引用上仍然大量出错，常见的有编造标题、作者错配、出处不符。更重要的发现是：**「检索原文 + 结构化比对」比「让大模型直接判断引用对不对」更可靠**。所以核验环节必须真的把原文抓回来比对，不能让模型凭印象判断。

#### 3.3.3 项目真实性体检清单

| 对象 | 体检信号 |
|---|---|
| **GitHub 项目** | 星数增长曲线是否有异常陡升；给星账号的质量（新号、空号比例）；提交历史（是否一次性提交、是否只有 README）；贡献者数量；Issue/PR 的响应情况；Release 节奏；README 宣称的功能与代码是否一致；**能否在沙箱中实际跑通** |
| **论文** | 是否经过同行评审；代码与数据是否公开；结果是否有人独立复现；作者与机构是否可查；引用是否真实存在 |
| **产品/公司** | 域名注册时间；团队成员能否交叉验证；融资记录；是否有真实定价页和用户；第三方评价是否只来自合作方 |
| **社交帖子/新闻** | 溯源到最早的原始出处；截图与原链接是否一致；发布时间；图片是否被篡改或挪用（反向搜图；支持的话检查 C2PA 内容凭证） |

最后给出一个 **「炒作指数」**：把「宣传声量」和「可验证的实质」对比，用一句话告诉你「热度大于实质」还是「被低估」。

### 3.5 两条落地路线

| | 路线 A：托管优先（推荐用于 MVP） | 路线 B：自建编排（推荐用于第三阶段以后） |
|---|---|---|
| 组成 | Claude Managed Agents（深度研究模板 + 自定义系统提示 + outcomes 评分标准 + 多 Agent 工作流）+ 自写的 MCP 工具 + 渲染脚本 | LangGraph 或 Temporal 编排 + Claude API + 同一套 MCP 工具 + 自建存储 |

| 缺点 | Beta 阶段 API 可能变化；对单一厂商有依赖 | 自己写循环、断点续跑、并发、重试；运维负担重 |

**推荐**：先走路线 A，2–3 周拿到能用的系统和真实使用数据；当你遇到托管平台满足不了的需求（比如必须混用模型、必须本地部署）时，再把编排层迁到路线 B。因为工具层和数据层是自己定义的，迁移成本可控。

### 3.6 输出格式引擎（落实你的格式规则）

```text
所有报告先生成 Markdown（唯一源文件）+ assets/ 图片目录
        │
        ├── 报告里没有图片 ──► 只交付 .md
        │
        └── 报告里有图片   ──► 交付 .docx（由 pandoc + Word 模板从 .md 生成），

```

三条配套规则：

1. **图表必须由数据生成**（matplotlib、Vega、Mermaid），不用 AI 生成的示意图冒充数据图，保证图和主张账本一致、可复核。

3. 用同一份 Word 模板保证字体、标题层级、页眉页脚统一，以后要导出 PDF 也是一行命令。

| 能做到 | 做不到（或做不好） |

| 快速汇集公开信息，覆盖面超过人工 | 获取封闭平台和付费墙内的信息 |

### 4.3 成本估算（按公开标价粗估，需上线后实测校准）

以一份「标准深度」的单项目尽调报告为例：

| 环节 | 模型/服务 | 用量假设 | 估算费用（美元） |
|---|---|---|---|
| 主控（规划、分析、写作） | Claude Opus 5.5（输入 $4 / 输出 $20 每百万 token；缓存读 $0.20） | 输入约 40 万 token（约 60% 命中缓存），输出约 4 万 | 约 1.5 |
| 研究子 Agent ×4 | Claude Sonnet 5.5（$2 / $10） | 输入合计约 120 万，输出约 6 万 | 约 3.0 |
| 批量抽取与初筛 | Claude Haiku 5.5（$0.10 / $0.50） | 输入约 150 万，输出约 10 万 | 约 0.2 |
| 主张核验（疑难项升级） | Claude Sonnet 5.5 | 约 40 条主张，输入约 60 万，输出约 4 万 | 约 1.6 |
| 搜索调用 | 搜索 API | 约 80 次 × 每千次 5–10 美元 | 0.4–0.8 |
| 沙箱运行 | 托管容器 | 约 1 小时 × 0.08 美元 | <0.1 |
| **合计** | | | **约 7（区间 4–12）** |

- **方向扫描或多项目对比**这类大报告：约 15–30 美元/份。
- **每月 20 份标准报告**：约 100–250 美元/月。
- **降本手段**：不急的任务走批处理接口（半价）；稳定的系统提示和工具定义开启提示缓存；简单子任务降低推理强度（effort）；网页正文先用便宜模型压缩再交给强模型。**真正的成本大头是「读网页正文」**：有第三方测算，返回的正文 token 成本可以是搜索费本身的 6–20 倍，所以抽取和压缩策略比选哪家搜索 API 更影响成本。

### 4.4 主要风险与对策

| 风险 | 严重度 | 对策 |
|---|---|---|
| **幻觉与引用错配**：报告写得很像真的，但引用对不上 | 高 | 主张账本 + 原文逐字比对 + 红队审查；正文只允许引用账本条目 |
| **提示注入**：被研究的网页里藏着「忽略之前的指令……」之类的攻击文本 | 高 | 网页内容一律当作不可信数据；沙箱里不放任何密钥（用凭证保险库在出口注入）；高风险工具（发消息、写文件到外部）走权限审批 |
| **运行陌生代码的安全风险**（沙箱复现时） | 高 | 只在一次性隔离容器中运行；网络白名单；不挂载任何个人数据 |
| **中文封闭平台数据缺失** | 中 | 报告里明确标注「未覆盖的信息源」；允许你手动粘贴或上传内容作为补充输入；不用灰色爬虫 |
| **成本失控**（Agent 陷入无限检索） | 中 | 每份报告设美元上限和轮次上限；可观测平台监控每份报告的花费 |
| **质量无法衡量**：不知道系统是在变好还是变差 | 中 | 第 0 阶段就建 15–20 个真实任务的评测集和评分标准，每次改动后回归测试 |
| **前沿 API 变化**（Beta 功能调整、协议不兼容升级） | 中 | 适配层隔离；锁定 SDK 版本；关注变更日志 |
| **版权与平台条款** | 低–中 | 个人研究用途；引用控制在合理篇幅并注明出处；遵守 robots 与平台条款 |

### 4.5 可行性结论

**可行，且现在是好时机。**两年前要从零搭的东西（Agent 循环、沙箱、长上下文、工具协议、专供 AI 的搜索 API），2026 年都能直接用。你的工作重心可以全部放在**差异化部分**：研究方法论、真实性判断、个人化分析、知识沉淀。剩下的主要不确定性是真实性判断能做到多准，以及中文封闭平台的数据覆盖。这两点不会让项目做不成，但会决定它的上限，需要在设计上诚实面对，而不是假装解决了。

## 5. 维度二：项目实现价值

### 5.1 个人效率价值（最直接）

| 指标 | 纯人工 | 使用本系统（估算） |

| 单个项目的研究时间 | 3–6 小时（检索、阅读、交叉验证、整理） | 你的投入约 15–30 分钟（发链接 + 读报告），系统异步运行 15–60 分钟 |

粗估**每月可节省 50–100 小时**（取决于你的研究频率）。

> **这个数字有一个前提**：你现在本来就会花这些时间做研究。如果你现在看到有趣的项目，通常只是收藏一下就过去了，那「节省的时间」是虚的，系统反而会**新增**你的阅读负担。这正是第 0 阶段要先验证的事。

### 5.2 决策质量价值（最重要）

- **少被炒作牵着走**：「炒作指数」和真实性体检能帮你在投入时间之前就过滤掉一部分噪音。
- **结论可追溯**：每个判断都能点开看证据，你可以快速判断「这条我信不信」，而不是整份报告全盘接受或全盘怀疑。
- **强制结构化思考**：每份报告都必须回答「对我意味着什么」「下一步做什么」，研究就不会停留在「知道了」。

### 5.3 知识资产价值（长期复利）

一年下来，几百份结构化报告和成千上万条带出处的主张，会自动形成你个人的**领域知识图谱**。新项目进来时，系统能说「这和你 3 月研究过的 X 很像，但在 Y 上不同」。这种连接能力是任何通用研究工具都给不了的。

### 5.4 能力与作品集价值

搭这套系统本身，就是一次完整的「2026 年 AI Agent 工程」实战，覆盖多 Agent 编排、工具协议、检索增强、事实核查、评测体系、成本优化、安全防护。如果你有求职、科研或创业方面的打算，这是一个**有深度、可演示、能讲清楚技术取舍**的作品。

| 竞品类型 | 代表 | 它们的优势 | 它们的不足（你的机会） |

| 通用深度研究 | ChatGPT 深度研究、Gemini 深度研究、Perplexity | 大厂资源、检索覆盖广、使用便宜（约 20 美元/月起） | 通用化，不了解你；真实性判断是隐式的；没有持久的个人知识库；一次性产出 |
| 通用 Agent | Manus、Kimi 等 | 任务范围广 | 不专注研究方法论与核验 |
| 开源深度研究 | Onyx、DeerFlow 2.0、Perplexica、Khoj | 可自托管、可定制 | 需要自己集成；真实性层普遍薄弱 |

**判断**：

- 正面硬碰「通用深度研究」，**没有商业胜算**。
- 有机会的细分方向是 **「可验证的尽调报告」**：面向需要对外部项目做判断的人（投资分析、技术选型、科研选题、竞品情报、媒体核查）。他们愿意为「每个结论都有证据链、可疑之处被明确标出」付费，因为他们的错误成本高。
- 建议**先把它当个人工具做到自己离不开**，积累 3 个月真实使用数据后，再评估是否产品化。

### 5.6 价值结论

|---|---|---|
| 个人效率 | 高 | 最确定，第一阶段就能兑现 |
| 决策质量 | 高 | 取决于真实性层做得多深 |
| 知识资产 | 高（长期） | 需要坚持使用 3 个月以上才明显 |

| 商业化 | 中低（目前） | 要找准细分人群并做出差异化 |

## 6. 维度三：你现在的决策方案是否对你有帮助

> 你要求不要只捧你，所以这一节先讲问题，再讲优点。

### 6.1 先说结论

**部分有帮助，但没打中要害，6/10。**这个方案能帮你搭出一个「会做研究的系统」，但不一定能帮你解决真正的问题。它在「怎么研究」上想得很多，在「为什么研究、研究完做什么、什么不用研究」上几乎是空白。

### 6.2 直说：方案的八个问题（按严重度排序）

**问题 1【要害】：优化错了对象。你要的是更好的判断，方案给的是更深的研究。**

你的输入是「网上看到的有趣项目」。这类输入的特点是：**量大、大部分是噪音、绝大多数不值得深挖**。真正稀缺的是「判断这个值不值得我花时间」，而不是「把每个都研究透」。六段链路每次都跑满，结果是一堆 20 页的报告，你读不完，也不会因此多做几个决定。这是把「收藏夹吃灰」升级成了「报告库吃灰」。

→ 对策：系统默认做**速判分诊**，只有少数输入进入完整链路（见 2.1 重构 0）。

**问题 2【要害】：需求还没验证，就先决定造工具。**

有个问题值得你诚实回答：**过去一个月，你有多少次是因为「研究不够深」而做错了决定，或者错过了机会？**如果答案是很少，那瓶颈不在研究工具，而在注意力、时间，或者行动力。这时造一个研究系统，可能只是「用搭工具代替做事」，搭工具的过程很有成就感，但不解决问题。

→ 对策：**先别写代码**。接下来 2 周，你把真实看到的项目发给我，我在对话里手工跑这套链路。只有当你发现这些报告真的改变了你的决定，才值得把它自动化。这样做零开发成本，还能顺便攒下评测集。

**问题 3：只定义了「怎么研究」，没定义「为谁、为什么决策」。**

六段链路是一份研究方法描述，不是产品定义。「交付成果汇报」交付给谁？用来做什么决定？读完之后的下一步动作是什么？这些不定义，「具体事务分析」这一段就只能写出通用的优缺点分析，和 ChatGPT 深度研究没有区别。

→ 对策：每份报告的第一行必须是**建议动作**（忽略 / 收藏 / 试用 / 深入投入），并写清楚「什么情况下应该改变这个判断」。

**问题 4：最值钱的「真实性判断」，是你定义得最少的一环。**

整个方案里，真实性判断是唯一真正能拉开差距的环节，但你只写了四个字。没有标准的真实性判断比没有判断**更危险**：AI 会很自然地写出「该项目整体可信度较高」这种听起来专业、实际上空洞的结论，让你产生虚假的安全感。

还有一个结构性问题：同一个 AI 先研究、再自己判断自己找来的信息真不真，是**既当运动员又当裁判**，它的错误是相关的。

→ 对策：真实性判断必须有明确的标准（见 3.3 节的来源分级、判定标签、体检清单），并且由**独立的核验环节**完成：重新抓原文逐字比对，用不同的 Agent 做红队审查。

**问题 5：精力花在了表层问题上。**

你的输出格式规则（Markdown / Word / 有图就转）写得比真实性标准还具体。这不是格式规则本身有错（它很务实），而是说明当前的注意力在「交付物长什么样」，不在「交付物对不对、有没有用」。格式是一个下午就能写完的脚本，不是需求的核心。

**问题 6：「使用世界上最新的技术」是技术驱动的信号。**

用户从「最新」里得不到任何好处，只能得到「好用」。前沿技术多半还在 Beta，接口会变，要花精力维护。更关键的是，你需要先回答：**做这个项目的首要目的，是「用起来省事」，还是「学技术、做作品」？**

| 如果首要目的是… | 那么正确做法是… |
|---|---|
| 用起来省事 | 最大限度用现成产品（ChatGPT / Gemini 深度研究 + 自己的提示模板），只自建真实性层和知识库 |
| 学技术、做作品 | 值得自建更多层，「最新技术」就是合理要求，但要接受它可能没那么好用 |

两个目标都想要，最后往往两头都做不好。你需要选一个作为主目标。

**问题 7：「集合多种功能的服务助手」，范围蔓延。**

你在同一段话里描述了两个不同的产品：一个是**专注的研究流水线**，一个是**什么都能干的助手**。「多种功能」具体是哪些，没有列出来。个人项目最常见的死法就是范围无限扩大，最后什么都做了一点，什么都不好用。

→ 对策：第一版只做一件事，就是「输入一个链接，输出一个可靠的判断」。其他功能做成以后可以插拔的技能，并且必须先证明自己有用。

**问题 8：长期把判断外包给 AI，有隐性代价。**

如果每个判断都由 AI 给出，你自己的信息辨别力会慢慢退化，而且会越来越倾向于相信自己没核实过的结论。

→ 对策：报告突出证据，而不是只给结论；高价值决定保留你的人工确认环节；定期抽查几条主张，看系统判定和你自己的判断是否一致。

### 6.3 方案里确实对的部分

只说成立的，不夸大：

- **把架构决策交给我，自己聚焦需求**：分工高效。但有些决定必须你来做（见第 8 节），尤其是上面问题 6 里的「首要目的」。

| **对比** | 一次给 2 个以上同类对象 | 同标准研究 | 对比表 + 选择建议 | P1 |
| **深度研究** | 你说「深度」，或者涉及投入真实资源的决定 | 30–90 分钟 | 标准报告 + 代码审阅 + 横向对比 | P1 |
| **跟踪** | `/watch 添加 <对象>`，之后每周自动跑 | 每周一次 | 只报告变化 | P2 |

### 9.6 什么时候再升级到路线 A（托管 Agent 平台）

出现下面**任一**情况再升级，不要提前：

1. 你想在手机分享菜单里一键发起，不想打开 Claude App。
2. 每周超过 20 份标准报告，订阅用量不够用。
3. 需要给别人用。
4. 需要真正长时间、无人值守的研究任务（单次超过 1–2 小时）。

迁移成本很低，因为方法论都在 Markdown 文件里：Skill 内容原样变成 Agent 的系统提示，`config/rubric.md` 变成「按评分标准迭代」的标准，`/watch` 变成定时部署，仓库结构不用变。

### 9.7 路线 0 的局限与风险（诚实说明）

| 局限/风险 | 说明 | 处理方式 |
|---|---|---|
| 要打开 Claude App 才能发起 | 不是「一键分享」 | 可接受；真受不了再按 9.6 升级 |
| 报告散落在多个分支 | 云端会话默认每次在一个新分支上工作，报告会分散 | 提示词里约定所有报告统一提交到一个固定分支（如 `main` 或 `reports`），需要你在会话里授权一次 |
| 单次会话有上下文和时长上限 | 深度研究读的网页多 | 阅读交给子 Agent，主会话只收摘要和主张；超出预算就停，并写明没做完的部分 |
| 运行陌生代码有风险 | 云端容器虽然是一次性的，但能推送到你的仓库 | **默认只读代码、不运行**；需要复现时先征得你同意；真正的隔离沙箱放到升级后再做 |
| 提示注入 | 被研究的网页里可能藏着攻击指令 | 网页内容一律当数据；Agent 只允许写 `reports/`、`watchlist.md` 等指定文件 |
| 中文封闭平台覆盖不到 | 公众号、小红书等没有可靠接口 | 支持你直接粘贴原文或截图作为输入 |
| 用量消耗 | 深度报告比较耗用量 | 默认速判；深挖需要你确认 |
